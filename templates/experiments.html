Experiment 01
Tamper Detection
50 tampered hashes injected

Objective: Evaluate how effectively each database model detects cryptographic hash tampering in the evidence chain. 50 evidence records had their stored SHA-256 hashes silently replaced with corrupted values to simulate tampering without modifying the file itself.

Method: Each database was queried independently using its native detection mechanism — SQL window functions comparing consecutive hash states, Neo4j graph pattern matching on VerificationEvent nodes flagged with mismatches, and MongoDB aggregation over the audit_logs collection. Detection counts and query latency were recorded.

Why this matters: In a forensic chain of custody, an undetected hash change means tampered evidence could be presented in court without anyone knowing. A detection system that misses injected tampering — or that is too slow to run routinely — is operationally useless.

✓
Neo4j is the most sensitive detector — it surfaced 87 anomalies against 50 injected, catching not only the direct hash mismatches but also cascading relationship inconsistencies in the custody graph that were introduced as a side-effect of tampering.
✓
Neo4j is also the fastest at 0.151s — 4.3× faster than SQL — because graph traversal follows pointer-based relationship edges in memory rather than performing index scans and hash joins.

Experiment 02
Broken Chain & Cycle Detection
30 gaps + 10 cycles injected

Objective: Assess the ability of SQL and Neo4j to detect two specific custody chain anomalies: broken chains (gaps where evidence moved from one user to another with no recorded handover event) and custody cycles (evidence returned to a previous holder without a valid return transfer, indicating possible unauthorized re-acquisition).

Method: 30 deliberate chain gaps were injected by removing intermediate custody log entries from the PostgreSQL coc_logs table and their corresponding Neo4j relationships. 10 cycles were injected by creating direct transfer relationships back to previous holders. Both databases were queried using their respective detection methods — SQL LAG() window functions for gaps and self-join patterns for cycles; Neo4j pattern matching for both.

Why this matters: Chain gaps invalidate the admissibility of evidence in court — there must be an unbroken record of who held the evidence at every point. Cycles indicate that sealed or transferred evidence was re-accessed without authorization, a serious forensic protocol violation.

Key Findings
✓
Neo4j is more precise for both detection types. For cycles, SQL flagged 1,462 evidence items (14,620% recall) versus Neo4j's 186 (1,860% recall). SQL's self-join cycle query matches any pair of events where a user appears twice in the custody sequence — this produces a massive combinatorial expansion of results rather than actual cycle paths.
✓
Neo4j is also faster for both tasks — 0.264s vs 0.557s for gap detection (2.1× faster) and 0.454s vs 0.767s for cycle detection (1.7× faster). The graph engine follows relationship paths directly without scanning entire log tables.
!
SQL's high recall figures reflect structural over-sensitivity. The LAG() window function and self-join patterns detect many historical anomalies that predate the injection, not just the 30 gaps and 10 cycles we deliberately introduced. This is useful as a broad audit sweep but produces too much noise for targeted incident investigation.
✓
Both databases successfully detect the injected anomalies — neither misses the injected patterns entirely. The difference is specificity: Neo4j returns actionable results; SQL requires post-query filtering to isolate the true positives.
Experiment 03
Insider Misuse Profiling
20 insider users simulated

Objective: Determine whether the multi-model system can identify insider threats — users who access or handle evidence at an abnormally high frequency relative to their peers — using statistical threshold-based detection across all three database models.

Method: 20 user accounts were marked as insider threats in the simulation dataset. Each database was queried using a statistical method: SQL used a subquery computing mean + 2σ of access counts to set a dynamic threshold; MongoDB used an aggregation pipeline computing the same threshold over the activity log collection; Neo4j used a graph degree-based metric counting outgoing PERFORMED relationships per user node. All three then applied the threshold to flag users above it.

Why this matters: Insider threats are among the most damaging attack vectors in forensic systems. An investigator with legitimate access who over-accesses evidence outside their assigned cases is difficult to detect without automated behavioral profiling. This experiment tests whether database-layer analytics can surface such patterns without requiring a separate ML pipeline.

!

This reveals that the bottleneck is not the database model but the detection algorithm: a simple statistical threshold (mean + 2σ) is insufficient to distinguish 20 injected insiders from 4 statistical outliers in the full population.
✓
Neo4j and MongoDB are 8× faster than SQL (0.077s vs 0.636s). For insider profiling, which must run continuously as a background task, this latency difference matters significantly — SQL's 0.636s per run becomes prohibitive at high scan frequency.
✓
MongoDB uses a lower threshold (115.4) because it counts distinct log documents per user rather than total access events — the document model naturally groups related actions differently, making its threshold more sensitive but its population distribution also different.
!
The low recall (5%) is expected and informative. Pure statistical outlier detection cannot identify insiders who are careful to stay near the mean. This experiment validates that the system needs a more sophisticated model — such as peer-group baselines, role-normalized thresholds, or time-of-day patterns — for production-grade insider detection.
Experiment 04
Query Performance Comparison
8 queries · 5 trials each

Objective: Benchmark the latency of representative queries across all three database models to empirically validate the multi-model architecture's performance claims. Each query type is matched to the database model best suited for it — the hypothesis is that SQL handles structured lookups efficiently, Neo4j handles traversals far faster than SQL, and MongoDB handles log aggregations faster than SQL.

Method: 8 queries were executed 5 times each against the live multi-model database (cold start excluded). Average, minimum, and maximum latencies were recorded. SQL queries run against PostgreSQL, Neo4j queries use Cypher over the bolt driver, MongoDB queries use pymongo with the aggregation framework. All tests ran against the same dataset produced by the simulation step.

Why this matters: The entire architectural argument for using three databases instead of one rests on performance. If Neo4j traversals were not faster than SQL JOINs, or if MongoDB aggregations were not faster than SQL GROUP BY, the added operational complexity would not be justified. This experiment provides empirical validation.

Key Findings
✓
Neo4j is dramatically faster for graph operations. Cycle detection (Q5) at 27ms is 21× faster than the equivalent SQL self-join (581ms). Chain traversal (Q4) is 11.9× faster. This empirically validates the core architectural argument: custody chains belong in a graph database.
✓
MongoDB is consistently faster for log analytics. Both Q6 (82ms) and Q7 (69ms) are 7–9× faster than comparable SQL GROUP BY queries. The document model's indexed collections and native aggregation pipeline are more efficient for append-heavy log data than relational table scans.
!
SQL remains necessary for structured metadata queries. Q1 (evidence by case) and Q2 (custody chain records) are only achievable with strong relational guarantees — JOIN integrity, FK constraints, and ACID semantics. No graph or document query can replicate the correctness guarantees of a relational lookup for these operations.
!
The combined query (Q8) is bounded by SQL latency (579ms) since it must wait for the PostgreSQL component to complete before assembling the response. This is the cost of multi-model integration — but it remains acceptable for interactive dashboard use and far better than loading all data from a single slow store.
